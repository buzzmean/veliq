# Восстановление доступа при неверном ответе DNS

Успешное открытие TCP через релей и хороший RTT не доказывают доступность HTTPS. В историческом сравнении системный DNS вернул для `web.telegram.org` адрес с окончанием `.40`, а независимые источники — `.99`: первый адрес принимал TCP, но возвращал `INVALID_TLS_RECORD`. Это наблюдение не является текущей проверкой Telegram и не закрепляет один из адресов в коде.

## Диагностика

`tools/windows/check-origin-dns.ps1` вызывает авторизованный метод `browser.origin.check`. Он сравнивает до трёх явно заданных публичных IPv4 на HTTPS/443 через действующий защищённый пул. Принимаются имя и адреса, но не произвольные пути, заголовки, cookie, ключ клиента или отключение TLS.

Каждая цель получает новое соединение и бюджет 1500 мс. Проверяются SNI и сертификат исходного имени, согласование HTTP, фиксированный `GET /` и ограниченный ответ. Диагностика возвращает этап, причину, полученные байты, HTTP-статус, ALPN и версию TLS. Общий бюджет — пять секунд. Метод не меняет профили, оптимизацию, DNS, PAC, активацию и серверные файлы.

Правильный сертификат и настоящий ответ одной цели при ошибке TLS другой могут подтвердить гипотезу неверного адреса в данном опыте. Отказ обеих требует разбора этапа, а не объявления сервиса исправным. Диагностический запрос не заменяет проверку страницы, входа и WebSocket в Chrome.

## Ограниченное восстановление

Обычный запрос начинает с системного DNS и политики домена. При ошибке разрешения или неподтверждённом соединении, включая несовпадение сертификата, HTTPS AUTO может использовать независимый ответ. Системный резолвер не заменяется; данные одного домена не определяют маршрут другого.

- DNS-запросы A в формате RFC 8484 направляются к `dns.google` через `8.8.8.8:443`, затем при необходимости к `cloudflare-dns.com` через `1.1.1.1:443`. Это адреса начального доступа к резолверам, а не закреплённые адреса сайтов. Соединение идёт через авторизованный релей с обычной проверкой сертификата имени резолвера.
- Допускаются два источника, две проверки кандидатов, два одновременных восстановления и до 512 записей. Сохраняется общий срок запроса и резерв 750 мс для нового туннеля Chrome. Бюджет восстановления — до двух секунд; отрицательные результаты и исчерпание ёмкости дают паузу 30 секунд. Одновременные одинаковые запросы используют один результат.
- Проверяются вопрос, тип, ID, код ответа, цепочка CNAME до восьми звеньев и размеры сообщения. Частные, локальные, служебные, зарезервированные адреса и имена локальной сети отклоняются. Перенаправления DoH не выполняются. TTL учитывает минимум цепочки, HTTP Age и консервативные ограничения Cache-Control.
- Сам ответ резолвера не означает успех. `DNS_RELAY_HTTP_VERIFIED` публикуется только после проверки сертификата исходного имени, HTTP 2xx/3xx и настоящих байтов ответа. Результат относится к точному проверенному назначению и защищённому пути, а не ко всему приложению.
- Ключ кэша включает приложение, имя, порт, схему, сеть, версию политики и релей. Срок положительной записи — не больше DNS TTL и пяти минут. TTL 0 разрешает использовать текущий результат без повторно пригодной записи. Новый неверный системный ответ не заменяет ещё действующее независимо подтверждённое назначение. Изменение сети или политики требует новой проверки.
- Явные `BLOCK`, `DIRECT`, локальные правила и подтверждённая базовая стратегия YouTube не переписываются. Защищённым назначениям не разрешается пробный прямой путь. Поддержка IPv6 и HTTP/3 этим механизмом не добавляется.

`INVALID_TLS_RECORD` не даёт основания считать соединение здоровым или обходить проверку сертификата. При отказе независимого подтверждения сохраняется политика назначения. Механизм не обещает исправление любого уже открытого или непрозрачного соединения и не выполняет HTTP-проверку каждого защищённого запроса заново.

## Проверки реализации

Интеграция использует настоящий mTLS/QUIC с одноразовым билетом, неверный DNS-адрес с открытым текстом вместо TLS, независимый DoH через релей и правильный HTTPS/H2 с полной проверкой доверия. Проверяются TTL, изоляция сетей, неправильные вопросы, частные адреса и отказ сертификата резолвера или назначения.

Нативный стенд Windows задаёт Chrome неверный адрес синтетической цели, затем требует действительный браузерный ответ, одноразовое значение и правильное назначение через релей. Одновременно проверяются обычный прямой сайт, локальная стратегия YouTube и защищённый сервис. Рабочие учётные данные и публичный Telegram в CI не используются.
