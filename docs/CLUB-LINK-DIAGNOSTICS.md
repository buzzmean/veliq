# Наблюдение TCP-соединений LanGame

Компонент `CLUB_LINK` пассивно читает полные таблицы TCP4/TCP6 Windows
раз в две секунды. Он учитывает только фактически наблюдавшиеся соединения
`ESTABLISHED` с частными адресами у проверенного через SCM процесса
`LanGameService` или его непосредственного рабочего процесса с тем же образом.
Номер порта и адрес сервера не предполагаются и не проверяются сетевыми пробами.

После положительного наблюдения два успешных полных снимка без установленного
соединения с тем же узлом создают `CONNECTION_LOST`. Несколько сокетов к одному
узлу объединяются: замена одного сокета другим не считается потерей связи.
Начальный пустой снимок, ошибка чтения, недоступный владелец процесса,
усечение таблицы и промежуток между снимками больше четырёх секунд не дают
основания объявлять потерю соединения.

Факт означает: «закрылось последнее наблюдавшееся TCP-соединение LanGame
с локальным узлом». Обычное переподключение приложения также может создать
такой факт. Сохранённые PID и время создания процесса при потере описывают
последнего проверенного владельца; повторное использование PID не переносит
его идентичность на другой процесс.

Новый положительный снимок создаёт `CONNECTION_RESTORED` для того же эпизода.
Это только наблюдение TCP: оно не подтверждает авторизацию, готовность LanGame
или доступность игровых дисков. VELIQ не перезапускает LanGame, не закрывает
соединения и не меняет LAN, iSCSI, службы или интерфейсы сети.

Если Windows сохраняет состояние `ESTABLISHED` при недоступном канале, этот
наблюдатель ещё не видит потерю связи. Прикладной отказ без закрытия TCP требует
отдельной проверенной сигнатуры журнала или API LanGame. Состояние SCM `RUNNING`
также не подтверждает связь с клубным сервером. Общие ошибки NETWORK,
STORAGE_ISCSI, proxy, TLS и пропуск heartbeat CP не заменяют этот факт.

Причина по умолчанию `UNKNOWN`. Совпадение по времени с ошибкой VELIQ или NIC
не доказывает виновность. Для иной оценки нужны положительные доказательства,
относящиеся к тому же соединению; отсутствие записи capture не доказывает
отсутствие воздействия VELIQ. Контекст берётся из ограниченного окна C03
по устройству, сеансу и времени, без содержимого пакетов и сырых сообщений.

Метаданные `club_link` содержат только тип, случайные идентификаторы узла и
эпизода, TCP4/TCP6, переход состояний и время последнего наблюдения
`ESTABLISHED`. Адреса и порты остаются в памяти службы. Факты получают новые
ID; старые записи Windows не переинтерпретируются. Запись в устойчивый журнал
предшествует ускоренной отправке по существующему подписанному каналу C03.
Ошибка диска не выдаётся за сохранённое событие; ускорение не отменяет
ограничение повторов после сетевого отказа.

Сначала развёртывается CP, принимающий необязательное поле `club_link`, затем
клиент. Схема БД 13 уже хранит ограниченный JSON, новая миграция не требуется.
Старые события сохраняют прежний JSON и digest. Старый CP со строгим JSON-
декодером отвергнет неизвестное поле, поэтому обратный порядок недопустим.
