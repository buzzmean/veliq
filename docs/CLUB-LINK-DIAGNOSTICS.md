# Наблюдение TCP-соединений LanGame

Компонент `CLUB_LINK` пассивно читает полные таблицы TCP4/TCP6 Windows
раз в две секунды. Он учитывает только фактически наблюдавшиеся соединения
`ESTABLISHED` с частными адресами у проверенного через SCM процесса
`LanGameService` или его непосредственного рабочего процесса с тем же образом.
Номер порта и адрес сервера не предполагаются и не проверяются сетевыми пробами.

После положительного наблюдения два успешных полных снимка без установленного
соединения с тем же узлом создают `CONNECTION_LOST`. Несколько сокетов к одному
узлу объединяются: замена одного сокета другим не считается потерей связи.
Начальный пустой снимок, ошибка чтения, недоступный владелец процесса,
усечение таблицы и промежуток между снимками больше четырёх секунд не дают
основания объявлять потерю соединения.

Факт означает: «закрылось последнее наблюдавшееся TCP-соединение LanGame
с локальным узлом». Обычное переподключение приложения также может создать
такой факт. Сохранённые PID и время создания процесса при потере описывают
последнего проверенного владельца; повторное использование PID не переносит
его идентичность на другой процесс.

Новый положительный снимок создаёт `CONNECTION_RESTORED` для того же эпизода.
Это только наблюдение TCP: оно не подтверждает авторизацию, готовность LanGame
или доступность игровых дисков. VELIQ не перезапускает LanGame, не закрывает
соединения и не меняет LAN, iSCSI, службы или интерфейсы сети.

Если Windows сохраняет состояние `ESTABLISHED` при недоступном канале, этот
наблюдатель ещё не видит потерю связи. Прикладной отказ без закрытия TCP требует
отдельной проверенной сигнатуры журнала или API LanGame. Состояние SCM `RUNNING`
также не подтверждает связь с клубным сервером. Общие ошибки NETWORK,
STORAGE_ISCSI, proxy, TLS и пропуск heartbeat CP не заменяют этот факт.

Причина по умолчанию `UNKNOWN`. Совпадение по времени с ошибкой VELIQ или NIC
не доказывает виновность. Для иной оценки нужны положительные доказательства,
относящиеся к тому же соединению; отсутствие записи capture не доказывает
отсутствие воздействия VELIQ. Контекст берётся из ограниченного окна C03
по устройству, сеансу и времени, без содержимого пакетов и сырых сообщений.

Метаданные `club_link` содержат только тип, случайные идентификаторы узла и
эпизода, TCP4/TCP6, переход состояний и время последнего наблюдения
`ESTABLISHED`. Адреса и порты остаются в памяти службы. Факты получают новые
ID; старые записи Windows не переинтерпретируются. Запись в устойчивый журнал
предшествует ускоренной отправке по существующему подписанному каналу C03.
Ошибка диска не выдаётся за сохранённое событие; ускорение не отменяет
ограничение повторов после сетевого отказа.

## Совместимость журнала при возврате клиента

762 сохраняет только известные ему поля диагностики. После его `LoadJournal`
и `Save` новое поле `club_link` исчезает, хотя ID, ACK и счётчик потерь остаются.
Чтобы доставка факта не зависела от восстановления архивного JSON, новый
producer одновременно сохраняет typed-поле и совместимый конверт в `operation`:

```text
CL1_4_<32 шестнадцатеричных символа A–F/0–9>_<UnixNano>
CL1_6_<32 шестнадцатеричных символа A–F/0–9>_<UnixNano>
```

Конверт содержит только случайный peer-ID, TCP4/TCP6 и время последнего
положительного наблюдения. Он укладывается в прежние 64 символа; современное
время даёт 58. `incident` уже хранит link-ID, `code` — тип перехода. Адрес,
порт, native error и Windows RecordID для этого не используются.

`EffectiveClubLink` читает оба представления без изменения события. Он требует
точного формата, положительных представимых наносекунд, полного происхождения
наблюдения и допустимого интервала времени. Если typed-поле и конверт заданы
вместе, их значения должны совпадать. Частичный, чужой или противоречивый
конверт не превращается в событие связи. Прежний typed-only факт принимается
совместимым CP, но конверт не может восстановить данные, уже утраченные до его
появления. Обычные прежние диагностические события сохраняют своё значение.

Подпись, audience и receipt вычисляются по исходному wire-batch, включая его
исходные `operation` и наличие либо отсутствие typed-поля. Неявного marshal-
преобразования нет. Только после проверки подписи CP создаёт отдельную копию
для БД: восстанавливает `club_link`, приводит его время к UTC и очищает служебный
конверт. Поэтому typed-only, typed+конверт и факт после старого журнала дают одну
неизменную запись с тем же ID. Подписанный повтор с другим peer-ID конфликтует.
ACK остаётся связан с исходным batch, поэтому его может проверить и применить
сам 762. Срез wire-событий, proof и batch при записи в БД не изменяются.

Сначала развёртывается CP с этой совместимостью, затем новый клиент. Схема13
уже хранит ограниченный JSON, новая миграция для конверта не нужна. Серверный
экспорт видит прежнее typed-поле с пустым `operation`. Возврат клиента на762
не требует изменения его официального бинарника; совместимый CP должен
оставаться доступен для очереди новых событий. Возврат CP на typed-only
декодер до доставки такой очереди несовместим. У старого клиента остаётся его
обычный интервал отправки; ускоренная отправка относится к новому producer.

Проверка `TestClubLinkActual762JournalProofIngestAndACK` компилирует helper с
неизменёнными core-пакетами точного исходника762
`0faa9aab69335c1b0024da32c880d21fa42ed6e5`. Она прогоняет реальный старый
`LoadJournal→Save→Load→Batch→Proof`, отправку в loopback CP с отдельной PostgreSQL
и старые `Receipt→Ack→Save→Load`. TCP4/TCP6 и потеря/восстановление проверяются
отдельно, вместе с потерями, ID, прежними ACK и повторной доставкой в новом виде.
Включение: `VELIQ_TEST_DOWNLEVEL_762=1` и `VELIQ_TEST_DATABASE_URL` только
одноразовой тестовой БД; точный git-объект762 должен быть уже доступен локально.
Тест не скачивает зависимости/SDK и не обращается к рабочему журналу или БД.
