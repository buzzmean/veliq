# CS2: варианты локальной UDP-фрагментации

Экспериментальный кандидат, не подтверждённое исправление игрового входа.
Непрерывный `udp-fragment-24` также не завершил вход: наблюдение на NIC
подтвердило 2216 полных пар с уникальными IP ID и 9 входящих ответов за
первые 496 мс; после этого входящих пакетов не было. Счётчики ответов
службы совпали с NIC. Причина потери вне этой точки не установлена.
Новые варианты проверяют гипотезу о видимости игрового заголовка в первом
фрагменте; это не доказательство блокировки DPI и не обещание обхода.

## Явное включение

В `local.set` профиль с `protocol: "udp"`, явно выбранной стратегией
`udp-fragment-8`, `udp-fragment-16` или прежней `udp-fragment-24`,
`continuous_udp: true`, `cutoff: 0` обрабатывает подходящие пакеты до конца
соединения. Нужны включённая конфигурация, точное приложение, порты и IP-цель.
Флаг не допускается для TCP, приманок или цепочек действий. При отсутствии
флага прежний предел `cutoff: 1..8` сохраняется.

Каждый механизм разбивает IPv4-датаграмму на два фрагмента, сохраняя
полезные данные UDP. Контрольная сумма UDP рассчитывается до разбиения,
DF сбрасывается, IP ID сохраняется. Число в имени — размер IP payload
первого фрагмента: 8 байт UDP-заголовка и соответственно 0, 8 или 16 байт
полезных данных. Смещение второго фрагмента — 1, 2 или 3 единицы по 8 байт.
Длина исходного IP-пакета должна превышать 20 + этот размер и быть не более
1500 байт. Нужен ненулевой IP ID, без IPv4 options и входной фрагментации.
Поведение и минимальная длина 45 байт для прежнего варианта24 сохранены.
Неподходящий пакет проходит без изменения. При ошибке отправки стратегия
для данного потока прекращается; исходная датаграмма отправляется напрямую.
Перезагрузка конфигурации не возобновляет преобразование старого потока.

Для пробы без VPS используется профиль CS2 `mode: "DIRECT"` с единственным
UDP-правилом `DIRECT_PLUS` на точный IP/порт, выбранную локальную стратегию
и `fallback: "FAIL_OPEN_DIRECT"`. У профиля тот же fallback. Не использовать
relay rules, `FLOW_RELAY_FALLBACK` или автоматический подбор relay.
Остальные соединения CS2 остаются DIRECT. Если сохранены gameudp
`enabled=true` и `local_only=true`, явное правило заменяет игровой ladder;
`GAME_PROFILE_OVERRIDDEN_OR_REMOVED` в таком режиме ожидаемо.

## Доказательства и ограничения

Существующий входящий UDP-наблюдатель теперь учитывает ответы обычных
нативных DIRECT/DIRECT+ потоков по обратному tuple и сохранённой идентичности
процесса. Завершённые, неизвестные, заблокированные, relay и адаптивные
прокси-потоки исключены. Его прежний фильтр ограничен IPv4 UDP с портом
источника от 1024. Новые WinDivert handles и версии DLL не добавляются.

Тесты проверяют более восьми последовательных датаграмм, сборку исходных
данных и контрольные суммы, изоляцию цели, сохранение параметра через IPC,
обновление конфигурации, отправку/ошибку отправки для всех трёх вариантов,
фактический checksum helper закреплённой DLL, учёт ответов и отсутствие
relay fallback. Для кандидата требуются полные Go race/vet/build Linux и
Windows, проверка фильтров настоящей закреплённой DLL и сборочный CI.

Счётчики и успешный CI не доказывают обход. Физический PASS требует входа
на карту и не менее 10 минут игры со свежими входящими пакетами, полной
историей наблюдений и нулевым приростом CS2 `relayed_bytes` и
`relay_reply_bytes`. Нельзя подтверждать успех по одному ответу, началу
загрузки или суммарному трафику. Этот кандидат не меняет установку сам;
применение нового кода требует отдельного обновления работающей службы.
