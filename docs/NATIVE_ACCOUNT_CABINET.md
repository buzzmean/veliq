# Личный кабинет в приложении

Кнопка личного кабинета открывает нативное окно WPF. Вход — почта и одноразовый
код, регистрация — тип «Пользователь» или «Клуб» и имя. Кабинет показывает
подписки, оплаченный срок/бессрочность, компьютеры и историю платежей из account API.
Создание платежа в этом окне не реализовано; наличие истории не подтверждает
готовность платёжного провайдера.

## Права и состояние

Сессия кабинета принадлежит вошедшему аккаунту и хранится только в памяти этого
окна. После закрытия окна для управления понадобится новый вход. Активация ПК
остаётся в службе и не зависит от закрытия кабинета. Это намеренно разные сессии:
гость клубного ПК не получает кабинет владельца из факта активации машины.
Выход немедленно очищает данные и отменяет запросы; запоздалый ответ старой
сессии не может заменить данные нового аккаунта. Cookies, код и пароль не
передаются по IPC, не сохраняются в preferences и не выводятся в журналы.

Перед отключением компьютера запрашиваются подтверждение пользователя и свежий
список принадлежащих аккаунту устройств. Account API остаётся окончательной
проверкой владения. Локальная надпись «бессрочно» не выдаёт право подключения:
используется серверный can_connect, а затем повторная серверная проверка
подписки, вместимости, типа аккаунта и device link.

Новый device link создаёт служба по прежнему IPC-контракту. Его подтверждение
допускается только на том же HTTPS origin и с корректным идентификатором.
Уже связанный ПК не перепривязывается входом в другой кабинет. Клубный режим,
локальные административные права и аварийное отключение не меняются входом.
Подготовка образа доступна лишь когда служба уже находится в этом состоянии;
окно не включает технический режим и не запускает установщик.

## Автоматическое подключение приложений

Основной экран сервисов объясняет автоматическое обнаружение. Добавление
программы, удаление правила и выбор ручного маршрута доступны в расширенных
настройках. Существующие правила не сбрасываются. Точные границы TCP/UDP/IPv6
описаны в AUTOMATIC_APPLICATION_ROUTING.md.

## Проверки

Модельные тесты проверяют чужие подписки, ошибку владения, закрытое подключение,
некорректный ответ сервера, смену аккаунта и ответ после выхода. Нативные Windows
проверки открывают реальные WPF окна с фиктивными API/IPC: неверный/верный OTP,
клубный кабинет, устройства, минимальный размер, выход и незавершённый профиль.
Они не используют настоящую почту и не меняют активацию или доступы компьютера.

Физическая приёмка отдельно: пользователь/клуб, занятый ПК, отозванное место,
истёкшая подписка, потеря account API и выход без потери активации. Не считать
CI доказательством этих сценариев на установленном VELIQ. ПК не перезагружать,
не выключать, не усыплять, не завершать сессию и не менять технический режим.
