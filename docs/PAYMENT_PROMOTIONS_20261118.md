# Исторический отчёт 18.11.2026 — правило акции заменено

Решением владельца от 19.11.2026 клубная акция изменена: 30% на первые 90 последовательных дней первоначальных мест первых 20 клубов, включая последовательные оплаты. Обычная цена — 299 ₽/ПК/30 дней, без скидок за срок. Комиссию оплачивает VELIQ. Описание «скидка на весь первый заказ» ниже сохранено исключительно как история прежнего поведения. Уже созданные платежи сохраняют свои суммы и полный срок.

Новая реализация подготовлена только в изолированной копии. Модель: club_promotion_entitlements + club_payment_orders; кандидат миграции 009, фактический следующий production-номер UNKNOWN. Новые заказы имеют immutable snapshot и idempotency key. CANCELED не освобождает квоту или объём; автоматического release API нет. Исторический T0/состав мест/покрытие не угадываются: миграция помечает прежние клубные резервы REVIEW_REQUIRED.

Персональная акция и тарифы не изменяются. Публикация, production-миграция, реальные платежи и запуск исторических команд из этого документа сейчас не разрешены.

# Тарифы и промокоды — решение владельца 18.11.2026

Это дополнение заменяет прежние цены клубов, общие скидки и распределение
комиссий в ТЗ 17.11.2026. Остальные условия разовой оплаты сохраняются.

## Подтверждено

| Срок | Личный тариф | Скидка игроку | Клуб, один ПК без промокода |
|---|---:|---:|---:|
| 30 дней | 399,00 ₽ | 0% | 299,00 ₽ |
| 90 дней | 1 137,15 ₽ | 5% | 897,00 ₽ |
| 180 дней | 2 154,60 ₽ | 10% | 1 794,00 ₽ |
| 360 дней | 3 830,40 ₽ | 20% | 3 588,00 ₽ |

Клубная цена умножается на число ПК. Скидки за срок — только для игрока.
Сроки равны 30/90/180/360 суткам, а не календарным месяцам. Сумма старого
заказа, оплаченные периоды, бессрочные подписки, устройства не пересчитываются.
Автосписаний нет. VELIQ не прибавляет комиссию к заказу. По сообщению владельца
в магазине Platega 100% комиссии оплачивает VELIQ. Перед публикацией на
контрольной форме проверены СБП и криптовалюта по 3,99 ₽ без доплаты;
после публикации владелец подтвердил настоящую оплату 3,99 ₽ через СБП.

Отдельный тестовый код: 99%, только player/1 ПК/30 дней, 399 → 3,99 ₽,
одна успешная покупка. Сервер проверяет account ID
`00000000000000000000000000000000` и соответствие подтверждённой почте владельца.
ID был проверен в предыдущем read-only этапе; при выпуске кода проверяется
повторно. Email из браузера не является доказательством принадлежности.

## Окончательно утверждённая клубная акция — публикация отдельно

Владелец окончательно утвердил: один случайный общий код, скидка 30% только
на ПЕРВУЮ успешно оплаченную покупку подтверждённого клуба. Период первой
покупки — 30, 90, 180 или 360 дней. Максимум 20 разных подтверждённых клубов,
один раз на аккаунт. Уже оплачивавший клуб не участвует, даже если никогда
не использовал промокод. На один ПК: 209,30 / 627,90 / 1 255,80 /
2 511,60 ₽ за 30/90/180/360 дней. Другие скидки не складываются с промокодом.
Скидка не сохраняется в тарифе/подписке после покупки.

Клубный профиль создаётся самостоятельно, независимого подтверждения клуба
в существующем onboarding нет. Добавлен отдельный административный допуск
`promotion_club_approvals`; профиль/обычная регистрация его не выдают.
Акция по умолчанию выключена. Правила больше не ожидают согласования.
Подтверждение клубного образа/ПК в onboarding не подтверждает реальность клуба.
Для безопасного ручного допуска владелец:

1. Независимо проверяет существование клуба и полномочия представителя
   (контакт по известному каналу клуба, название/адрес и связь с аккаунтом).
2. Сверяет прошлые оплаты по всем аккаунтам этого клуба, включая счета и
   сведения вне VELIQ. Самодекларации заявителя недостаточно.
3. Выбирает подтверждённый account ID и присваивает реальному клубу стабильный
   неприватный идентификатор `club_reference` в своём реестре. Не создавать
   новый reference тому же клубу при смене почты/аккаунта.
4. Выполняет root-only `approve-club` с подтверждением проверки и reference.
   Уникальность reference в БД не допускает два аккаунта одного проверенного
   клуба. В БД хранятся reference, account ID, время и минимальный audit;
   документы/персональные сведения проверки остаются у владельца вне Git.

Обычный пользователь не может выдать себе этот допуск через profile API,
подтверждение почты или управление образами.

## Реализация

Миграция 008 только добавляет promotions/approval/reservations. Она не создаёт
кампаний, не включает их и не меняет существующие записи. В БД хранится только
SHA-256 с разделением назначения от 256 случайных бит кода. На каждый вид
акции допускается одна кампания; новая выдача не сбрасывает использованный код.
008 ещё не публиковалась; её draft дополнен уникальным club_reference. Если
перед публикацией на сервере уже окажется версия008, остановиться и подготовить
отдельную миграцию, не считать новую колонку автоматически установленной.

`POST /api/v1/account/subscriptions/{id}/quote` проверяет принадлежность,
обычный оплачиваемый тариф, вид аккаунта, допуск, срок, доступность кода и
возвращает базовую сумму, скидку и итог в копейках. Preview не резервирует место.
`/pay` принимает `promo_code` и повторяет проверку/расчёт; сумма браузера —
только проверка ожидания покупателя. Ни скидка, ни итог клиента не принимаются
как источник цены. В UI код хранится только в памяти текущей формы.

Создание льготного заказа: блокировка аккаунта, затем кампании → проверка
истории успешных покупок, лимита и уникальности → pending payment с суммой/сроком и
уникальным `reservation:<id>` → commit → один POST провайдеру → привязка
provider ID → выдача ссылки. Резервы и погашения вместе занимают максимум 20
мест. Код не попадает в reference, payload, metadata провайдера или аудит.
Адаптер Platega сохранён. CONFIRMED, включая API-сверку, погашает резерв и
начисляет срок атомарно в одной транзакции. Повторы не расходуют новое место.

Проверка первой покупки охватывает все подписки аккаунта и всех провайдеров,
включая ручные оплаты. Успешная запись с положительной суммой исключает акцию
навсегда; возврат/спор не обнуляет историю покупки. Бесплатное ручное
предоставление доступа с суммой0 не является оплаченной покупкой.
Старые pending/canceled требуют сверки: их возможный поздний CONFIRMED нельзя
игнорировать при проверке «первой». Старые записи не меняются и не пересоздаются.

Обычная новая покупка клуба теперь также получает pending-строку до запроса
провайдеру. Это закрывает окно, когда обычная покупка уже создаётся, но ещё
невидима проверке промокода. Общая блокировка аккаунта сериализует обычный
заказ, проморезерв и ручное начисление. При конфликте ручного начисления с
проморезервом оператор получает явный отказ для сверки, а не вторую покупку.
Серверный контракт Platega не меняется. Только для новых обычных клубных
заказов reference имеет префикс `club-order;`; неизвестный результат можно
сверить тем же admin reconcile. При этом promotion_state=`not-applicable`.

Ошибка/таймаут/отмена запроса создания не дают повторить POST с тем же кодом.
Неопределённый резерв не имеет автоматического TTL. CANCELED также не
освобождает резерв: поздний CONFIRMED должен остаться безопасным. Обычная
повторная покупка аккаунта с незавершённым проморезервом блокируется API.
Это консервативное ограничение: недошедшие до оплаты попытки временно занимают
места. Автоматическое освобождение без доказательства невозможности поздней
оплаты не реализовано. Для первого выпуска это осознанная защита от перепродажи
одного слота; улучшение освобождения требует отдельного доказанного протокола.

Если ответ создания потерян, оператор находит транзакцию в кабинете Platega.
`POST /api/v1/admin/promotions/reconcile` под существующей admin-авторизацией
принимает только `payment_id` и `provider_payment_id`, делает GET к Platega,
проверяет ID, Merchant ID, валюту, сумму, payload/подписку и только потом
привязывает/обрабатывает заказ. Повторный вызов идемпотентен. Он не создаёт
транзакций, не освобождает отменённые резервы и не сбрасывает погашенные коды.
Если транзакция у провайдера не найдена, не угадывать ID и не повторять POST.

Возвраты/споры сохраняются существующим механизмом payment_review_events;
погашенный код не восстанавливается. Доступ автоматически не отзывается.
Review до успешного подтверждения блокирует автоматическое начисление и
оставляет резерв для ручного разбора.

## Безопасная выдача после отдельного разрешения

`tools/promotion-admin.py` выполняется локально на Linux от root, обращается
к локальной PostgreSQL через runuser, не требует пароля в argv. Сам скрипт
не применяет миграции. Реальный запуск сейчас не выполнялся.

1. Создать новую директорию вне Git/синхронизации, root:root 0700.
2. `issue-owner --database <db> --output <новый-файл>` или `issue-club` создаёт
   только выключенную кампанию и записывает код один раз в новый файл 0600.
   Стандартный вывод содержит только ID/путь/статус, не код или его хеш.
   При ошибке не перезаписывать файл/кампанию; проверить состояние отдельно.
3. Владелец забирает файл через защищённый SFTP либо помещает код прямо в свой
   менеджер паролей. Не использовать чат Codex, Git, аргументы CLI или логи.
4. `enable --id <campaign-id>` — отдельное действие после разрешения.
   Для клубной акции дополнительно нужен `--confirm-club-rules`.
5. Для каждого независимо проверенного клуба:
   `approve-club --id <account-id> --club-reference <стабильный-id-клуба> --confirmed-club-verification`.
   Это административная проверка, а не автоматическая верификация организации.

`disable --id <campaign-id>` запрещает новые применения; существующие
заказы и обработка их подтверждений продолжаются. Резервы и минимальный аудит
не удалять даже после возврата денег или окончательного отключения акции.

Откат без потери оплаченных заказов:

- При необходимости вернуть цены/файлы сайта согласованной парой; сумма

  новый backend; старый бинарник не знает про атомарное погашение промокодов.
- Возврат старого бинарника допустим только до первого проморезерва и нового

- Аварийное отключение всего Platega — отдельная процедура существующего
  runbook: перед выключением pending/reconciliation, guard publish=false
