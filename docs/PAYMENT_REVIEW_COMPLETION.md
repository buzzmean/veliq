# Завершение проверки частичного возврата

Оператор может завершить проверку уже оплаченного заказа с подтверждённым
частичным возвратом. События провайдера и отдельное решение остаются в аудите.
Новый возврат или спор снова открывает проверку. Старое событие само по себе
больше не оставляет кнопку проверки навсегда и не блокирует следующий заказ.

Механизм выключен по умолчанию. Серверный параметр
`-payment-review-resolution` разрешает защищённые администраторские методы:

- `GET /api/v1/admin/payments/{id}/review` — текущий снимок и `last_event_id`.
- `POST /api/v1/admin/payments/{id}/review/resolve` — решение оператора.

Требуется прежняя администраторская Bearer-авторизация. Сессия кабинета и токен
клубного проверяющего не дают этого права. Ответы запрещено кешировать.
Администраторские API не следует публиковать через клиентский reverse proxy.

```json
{
  "last_event_id": 123,
  "evidence_sha256": "<64 строчных шестнадцатеричных символа>",
  "outcome": "review_completed_no_access_change"
}
```

Сервер сам читает провайдера заново; данные запроса не заменяют проверку.
Допускается только `PARTIALLY_REFUNDED` с `refundStatus=Succeeded`, теми же
подпиской/транзакцией/суммой/refundID и положительным возвратом меньше исходной
суммы. При отсутствии у провайдера полей возврата результат неизвестен и решение
отклоняется. Поддержку этих полей реальным API следует подтвердить отдельно;
ответы стендового эмулятора не являются такой проверкой.

SQL-блокировки следуют порядку аккаунт → подписка → платёж. После сетевого
чтения сверяются последний eventID, его фактические поля и принадлежность.
Общий десятисекундный бюджет включает провайдера, ожидание блокировок и commit.
Новый event или изменившийся снимок дают `PAYMENT_REVIEW_CHANGED`, повтор с
другим доказательством — `PAYMENT_REVIEW_RESOLUTION_CONFLICT`. Точный повтор
возвращает прежний результат без второй записи решения или аудита.

Добавочная миграция17 не изменяет прежние записи. Решение нельзя обновить или
удалить. Кабинет показывает, например: «Частичный возврат 3,95 ₽ · проверка
завершена», сохраняя исходную оплату3,99 ₽ в истории. При новом событии снова
отображается требование проверки.

Ни деньги, ни срок доступа, ни бессрочные права, ни устройства не меняются.
Разрешено завершить только tracking собственного уже зачисленного personal
order; callback не зачисляется повторно. Другие pending/canceled заказы и
резервы не освобождаются. Исторические финансовые guards выдачи кредита,
промокодов и реферальных наград сохраняются: решение не создаёт новую льготу.
`DISPUTED`, `CHARGEBACKED`, полный или незавершённый возврат требуют отдельного
финансового решения; этот метод их не закрывает. Вся история должна относиться
к одному refundID и той же сумме частичного возврата: прежний спор, другой
возврат или неоднозначная сумма не закрываются последующим partialсобытием.

Изменение подготовлено на тестовой коммерческой ветке поверх PR101. Рабочий
сервер, сайт, реальные платежи и возвраты при проверках не используются.

Для браузерной приёмки `tests/frontend/trial_offers_staging.py` поддерживает
`--scenario offers` и `--scenario refund`. Каждый сценарий запускается с новым
`TestStagingBrowserAcceptanceServer` и своей изолированной PostgreSQL-схемой:
повторные серии не обходят реальные лимиты входа на старом процессе. Проверяются
реальные API/БД/Chromium1440/390/360, без подмены ответа кабинета. Только fixture
подготавливает синтетическую оплату и возврат; операторская свежая проверка
провайдера отдельно проверяется HTTP/PG-тестами. Для fixtureURL передаётся только
тестовая cookie; её рабочий Path не расширяется. Физический телефон не проверялся.
