# Platega: подключение и проверка разовой оплаты

Утверждённые условия: [ТЗ от 17.11.2026](PLATEGA_ONE_OFF.md).
Результаты конкретного запуска: [приёмка](PLATEGA_ACCEPTANCE_20261117.md).

## Реализация

Кабинет получает `payment_terms` от API. `POST /api/v1/account/subscriptions/{id}/pay`
принимает `{months: 1|3|6|12, auto_renew: false, expected_amount_kopecks: ...}`.
Отсутствующий `months` совместим со старым запросом на 30 дней. Неверный JSON,
посторонние поля, промокод, неподдерживаемый срок и автопродление отклоняются.
Сумма рассчитывается сервером в целых копейках: цена за 30 дней × места × месяцы
× (100 − скидка). Для пользователя разрешено одно место. `expected_amount_kopecks`
проверяет согласие с показанной ценой, а не задаёт стоимость.
Планы с периодом, отличным от 30 дней, закрыты для этого сценария.

В `payments` сохраняются сумма, дни и `reference` с месяцами, скидкой, местами
и базовой ценой. Изменение конфигурации после создания ссылки не меняет заказ.
Только CONFIRMED зачисляет период: max(момент подтверждения, paid_until) + дни.
Сумма, валюта, принадлежность подписке и транзакция проверяются до зачисления.

При задержке webhook пользователь нажимает «Проверить оплату» в истории:
`POST /api/v1/account/payments/{локальный id}/refresh`. Сначала проверяются
сессия и владелец, затем выполняется серверный GET `/transaction/{id}` в Platega.
Merchant, id, payload, валюта и сумма сверяются; таймаут не меняет оплату.
Не чаще одного запроса к провайдеру за 15 секунд на платёж, включая разные вкладки.
Webhook и сверка используют одну транзакционную функцию зачисления.
Возврат на сайт сам по себе ничего не активирует. Повторять оплату при уже
списанных деньгах не нужно: использовать сверку и при необходимости поддержку.

`payment_review_events` хранит DISPUTED, CHARGEBACKED, PARTIALLY_REFUNDED,
refundId/refundStatus и накопленную возвращённую сумму без секретов и сырых тел.
Повторы одинакового события не создают вторую запись. Доступ не отзывается;
если спор пришёл раньше CONFIRMED, автоматическое зачисление блокируется до
разбора оператором. Разбор в кабинете Platega обязателен; отдельный процесс
автоматических возвратов/отзыва доступа не добавлен.

## Подготовка сервера

1. Установить фактические сайт/API/версию бинарника и схему БД. Не ориентироваться
   на старый адрес из документации. Проверить изменения других операторов.
2. Сохранить бинарник, unit/drop-ins, планы, изменяемые файлы сайта/nginx и
   `pg_dump -Fc` в root-only backup. Проверить SHA256, `pg_restore --list` и
   восстановление дампа в изолированную БД до изменения рабочего бинарника.
3. Проверить TLS сайта и upstream, `/api/v1/account` (401 без сессии), SMTP TLS,
   свободное место, отсутствие незавершённого обновления и доступность отката.
4. Сохранить имеющуюся production-миграцию 006 (бессрочные подписки). Платёжная
   миграция — 007. Проверить её на копии БД. Откат не удаляет новые таблицы и
   не восстанавливает старую БД поверх новых платежей/отзывов устройств.
5. Использовать `deploy/vps/plans.platega.json` для цен 399/199, периодов 30 дней
   и прежних идентификаторов `player-month`/`club-month`. Существующие подписки
   и места не пересоздавать; сверить plan_id перед установкой.
6. В nginx добавить только точный `location = /api/v1/payments/webhook` с
   проверкой TLS upstream. Общий запрет других `/api/` сохранить. Не применять
   лимиты входа по email к webhook. Заголовки X-MerchantId/X-Secret передаются
   только upstream; не включать их, тела запросов и cookies в журналы.

## Установка ключа владельцем

Не передавать ключ в чат, аргументы команд, Git, историю shell или логи.
На сервере API через доверенную SSH-сессию открыть защищённый файл редактором:

```sh
sudo install -o root -g neexitlag-control -m 0640 /dev/null /etc/neexitlag/control/platega.secret
sudo nano /etc/neexitlag/control/platega.secret
```

Имя группы сначала сверить с группой службы. Если файл уже существует,
команду `install ... /dev/null` НЕ выполнять: она обнулит ключ; открыть существующий
файл и проверить права. Вставить ключ одной строкой в редактор, сохранить.
Merchant ID не является API-ключом; сохранить его отдельно, без отправки в чат.
Добавить к существующему ExecStart только:
`-plans-file /etc/neexitlag/control/plans.platega.json`,
`-platega-merchant-id <merchant id>` и
`-platega-secret-file /etc/neexitlag/control/platega.secret`.
Существующие параметры TLS, SMTP, устройств, relay и enforcement сохранить.
Не использовать `-platega-base-url` в production.

Перед включением проверить backup и откат, перечень способов в Platega:
только уже согласованные СБП и криптовалюта. Сохранить комиссии 4/4% и 2,5/2,5%.
Новые способы и recurring не включать. Затем daemon-reload и перезапуск только
control-plane. Проверить health, вход, тарифы, сохранность мест и бессрочных прав.

Callback URL: `https://veliqapp.ru/api/v1/payments/webhook`.
Сначала проверка маршрута с поддельными заголовками должна дать
`400 PAYMENT_EVENT_REJECTED` при включённом адаптере (404 PAYMENT_NOT_CONFIGURED
означает, что маршрут может работать, но адаптер выключен). Затем владелец
сохраняет URL в Platega. Нельзя пересылать тестовый CONFIRMED с действующим
секретом для имитации реальной покупки.

## Приёмка с владельцем

На отдельной обычной подписке, не на бессрочной, выбрать срок и проверить сумму,
скидку, дни и места. На форме Platega владелец проверяет доступные способы и
финальную сумму с комиссией, затем сам подтверждает оплату.
Сопоставить id транзакции, сумму, CONFIRMED, запись payments и новую paid_until.
Повторная доставка/сверка не должны менять уже начисленный срок. Проверить также
отмену и задержку уведомления. Не публиковать реквизиты покупателя/секреты в отчёте.

Один реальный успешный платёж не подтверждает все периоды и оба метода.
Матрица: player и club (несколько ПК), 1/3/6/12 месяцев, новая покупка/продление,
СБП/криптовалюта, отмена, доставка webhook, сверка API. Отметить отдельно,
что проверено реально, что на mock, а что осталось непроверенным.

Для операторской сверки использовать read-only запрос:

```sql
SELECT p.id, p.provider_payment_id, p.amount_kopecks, p.period_days, p.status,
       p.created_at, e.provider_status, e.refund_id, e.refund_status,
       e.refunded_kopecks, e.received_at
FROM payments p LEFT JOIN payment_review_events e ON e.payment_id=p.id
WHERE p.provider='platega' AND (p.status='pending' OR e.id IS NOT NULL)
ORDER BY p.created_at DESC;
```

Не зачислять вручную без сверки реальной транзакции; не запрашивать сумму или
срок у браузера. При таймауте создания не повторять зачисление по догадке.
Если ссылка создана, но запись заказа не сохранилась, API не отдаёт ссылку
пользователю; неизвестные webhook отклоняются. Такие случаи разбираются с
провайдером, без выдачи доступа по одному return URL.

Контракт проверен по [официальной документации Platega](https://docs.platega.io/):
создание платежа без заданного метода, GET `/transaction/{id}`, callbacks.
Локальные mock-тесты не подтверждают настройки магазина и живую оплату.
