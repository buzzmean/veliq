# Онлайн-поддержка сайта

Виджет справа снизу работает на всех страницах, использующих `assets/site.js`.
Посетителю не нужны почта и регистрация. Специалисты отвечают через отдельного
Telegram-бота в закрытой группе. Только явно разрешённые числовые Telegram ID
могут брать и обслуживать обращения. Пользователь видит «Специалист VELIQ»;
личные Telegram ID и данные других клиентов в браузер не передаются.

## Сценарий

1. Посетитель открывает виджет и отправляет первый текст (1–2000 символов).
   Сервер создаёт тикет `queued` и запись в надёжной очереди уведомлений.
2. Бот публикует сообщение с кнопкой «Взять в работу». Первый разрешённый
   специалист атомарно становится владельцем (`assigned`). Второй захват
   отклоняется. Повторное нажатие не изменяет назначение.
3. Специалист использует Telegram «Ответить» на любое сообщение бота этого
   тикета. Текст сохраняется на сервере и появляется в виджете при ближайшем
   опросе (4 секунды при открытом чате). Вложения пока не поддерживаются;
   бот сообщает об этом, не выдавая их за отправленные.
4. «Вернуть в очередь» доступно текущему специалисту. Другой специалист
   сможет взять обращение. Оператор не может сам пометить проблему решённой.
5. Крестик, Escape и повторное нажатие на кнопку поддержки открывают выбор:
   «Свернуть», «Вопрос решён — завершить», «Продолжить диалог». После ответа
   специалиста над полем ввода появляется «Ваш вопрос решён?». «Нет, нужна помощь»
   возвращает фокус в поле. Сворачивание и отмена оставляют обращение открытым.
   Подтверждённое завершение переводит его в `resolved`; существующий durable
   outbox отправляет в Telegram уведомление «Пользователь подтвердил решение.
   Тикет закрыт.» с номером обращения, без кнопок назначения. Старые кнопки
   Telegram могут оставаться в прежних сообщениях; сервер отклоняет действия
   по закрытому обращению.
   Если новый ответ пришёл во время подтверждения, сохранённая revision вызывает
   конфликт: сначала прочитать ответ. При транспортной ошибке повторяется тот
   же key/ticket/revision. Двойное нажатие не создаёт вторую операцию.
6. Перезагрузка страницы/переход по сайту/закрытие вкладки не меняют статус.
   После решения можно начать новый вопрос. История текущего обращения
   доступна с пагинацией по 100 сообщений; старые записи не обрезаются в БД.

## Хранение и безопасность

- Отдельная служба `services/support/cmd/support` и **отдельная PostgreSQL БД**;
  не меняет схемы CP, подписок, relay или SMTP. Вход проверяется через account API. Новых Go-зависимостей нет.
- Миграция выполняется явно `-migrate`, а не при обычном старте. Повтор безопасен.
  Подключение: локальный сокет/loopback PostgreSQL либо TLS `verify-full` для
  удалённой БД. Не использовать рабочую БД control-plane.
- 256-битная случайная cookie `__Host-veliq_support_v2`, Secure/HttpOnly/SameSite=Strict,
  Path=/, без Domain. В БД хранится только SHA256 токена. Срок доступа — 30 дней.
  В localStorage не хранятся сообщения и секреты; sessionStorage содержит лишь
  состояние окна и номер прочитанного ответа. Это описание гостевого доступа; аккаунт восстанавливает собственную историю после входа.
- На общем ПК кнопка «Скрыть переписку на этом ПК» отзывает доступ сервером и
  удаляет cookie. Это не объявляет проблему решённой. Само закрытие окна не
  отзывает cookie. Завершайте сессию перед передачей общего браузера другому человеку.
- API поддержки находится под `/api/v1/account/support/`: туда браузер отправляет
  существующую HttpOnly cookie ЛК с Path=/api/v1/account. Служба проверяет её
  через фиксированный HTTPS `/api/v1/account` на каждом запросе, без редиректов,
  с проверкой цепочки/имени сертификата и лимитами времени/ответа. CP/подписки
  не изменяются. Непроверенный/истёкший аккаунт не становится гостем автоматически.
- Владелец account-истории определяется только постоянным `account_id` из ответа
  CP, никогда почтой или клиентским заголовком. Старый CP без этого поля вызывает
  безопасный отказ проверки; переносить историю по совпадению почты запрещено.
  Дополнение account API аддитивно и не требует миграции CP. В support-таблицах
  хранится хеш разделённого пространства владельцев, не почта и не session token.
- Гостевые и account-владельцы разделены и в SQL. Старые сессии неопределённого
  владельца помечаются legacy и отзываются миграцией; обращения остаются у
  операторов. Гостевую переписку нельзя автоматически присвоить вошедшему.
- POST требует совпадения `X-Support-Context` с текущей проверенной сессией:
  черновик/resolve из старой вкладки не отправляется от нового аккаунта.
  Logout/вход немедленно очищают UI во всех вкладках; запоздалые ответы отбрасываются.
  При возврате фокуса история скрыта до повторной проверки, черновик восстанавливается
  только для той же сессии. Сообщения/черновики не пишутся в browser storage.
- `support-auth.js` встроен в site.js перед загрузчиком виджета; account.js не меняется.
  Nginx отзывает гостевую cookie на login/verify и logout независимо от доступности
  поддержки. Выход авторизованного пользователя через виджет завершает его ЛК-сессию,
  история остаётся за аккаунтом. Старый `/api/v1/support/*` отвечает410.
- POST требует точного Origin и JSON; нет CORS. Размер тела ограничен 16 KiB.
  Чужие тикеты недоступны по ID. Текст показывается через textContent, Telegram
  parse_mode отключён. Авторизация по username/пересланному тексту не используется.
- Лимиты БД: 20 действий/минуту на посетителя; 120 сессий, 60 новых тикетов,
  600 сообщений/действий в час на IP; максимум 5000 нерешённых тикетов, 2000
  сообщений в тикете. IP хранится только как хеш ключа короткого счётчика.
  Nginx ограничивает частоту и размер запросов до службы. Это базовая защита;
  массовая распределённая атака потребует внешней защиты/дополнительного допуска.
- Уникальный ключ запроса предотвращает повторное сообщение при сетевом retry.
  update_id Telegram и offset сохраняются транзакционно с обработкой.
- Уведомления отправляются через durable outbox с задержкой до 5 минут при
  сбоях; порядок внутри тикета сохраняется. Если Telegram принял сообщение,
  но ответ API/фиксация БД потеряны, уведомление в группе может повториться:
  Bot API не предоставляет exactly-once sendMessage. Ответы и назначение тикета
  при этом не дублируются. Отвечать следует только на сообщения, распознанные ботом.
- Один poller удерживает advisory lock БД; несколько poller для одного бота
  в разных БД не допускаются. Используется getUpdates, публичного webhook нет.
  Существующий webhook того же бота надо отдельно убрать при подключении.
- Очистка ежечасно при работающем worker: сообщения/тикеты после 90 дней
  без активности, idempotency 30 дней, update ID 7 дней, истёкшие лимиты.
  Очистка по сроку не помечает тикет решённым. При отключённом worker очистка
  не выполняется; учитывать при длительном отключении поддержки.
- Telegram — отдельная копия переписки. Настроить автоудаление в закрытой группе
  (рекомендуется 7 дней); копии операторов и резервные копии БД имеют отдельные сроки.
  Не отправлять пароли, коды, платёжные данные и диагностические файлы с секретами.

## Подключение подготовленного бота

Ниже порядок для отдельного согласованного развёртывания; он не запускается тестами.

1. Создать бота через официальный BotFather, добавить в закрытую группу.
   Privacy Mode оставить включённым, права администратора не нужны.
   Разрешить отправку сообщений; каждый оператор отправляет `/start@имя_бота`.
2. На доверенном административном терминале выполнить `python3 deploy/support/inspect-bot.py`. Токен вводится скрыто и не сохраняется; скрипт не отправляет сообщений и не подтверждает updates. Без вывода токена в лог получить через Bot API getMe/getWebhookInfo/getUpdates
   числовые `message.chat.id` и `message.from.id`. Сверить группу и каждого
   оператора с владельцем; не включать неизвестные ID автоматически. Для сбора
   ID использовать защищённый ввод в локальной задаче настройки, не адресную
   строку браузера, shell history или стороннего бота. Обновления старше 24ч
   Telegram может удалить — при необходимости отправить новую команду.
   Настройку выполняет техническая задача, а не владелец вручную. После проверки
   ID используется `inspect-bot.py --configure --expected-username veliqsupbot
   --group-id <ID> --operators <ID1,ID2>`: проверяет правильного бота, Privacy Mode,
   отсутствие webhook, закрытую группу и членство; затем задаёт имя/описания,
   убирает неработающие команды из меню и читает настройки обратно. Токен
   вводится скрыто. При запуске под root на сервере `--save-token
   /etc/veliq-support/telegram-token` создаёт НОВЫЙ файл0600 в защищённом каталоге,
   не заменяет существующие файлы и не следует symlink. Пользователю достаточно
   скрытого ввода токена; групповые ID/allowlist собирает и сверяет техническая задача.
3. На сервере сайта подготовить отдельного системного пользователя, БД/роль,
   закрытые root-owned файлы `/etc/veliq-support/database-url` и
   `/etc/veliq-support/telegram-token`, mode0600. Токен вводить без эха,
   не через аргументы процесса/командную историю. Службе передавать только
   systemd LoadCredential. Без token-file сервис показывает «Чат пока не подключён»
   и не принимает новые обращения; нельзя выдавать это за работающую поддержку.
4. Сохранить и проверить backup сайта/nginx и отдельной БД. Собрать проверенный
   исходный коммит: `go build -trimpath -o support ./services/support/cmd/support`.
   Применить `-database-url-file <закрытый файл> -migrate` только к support БД.
5. Установить unit из `deploy/support`, затем отдельный Telegram drop-in с ID
   группы и операторов. Для выхода нужны HTTPS443 к api.telegram.org и проверяемый
   TLS. Бинарник не допускает внешний listen, стартует на127.0.0.1:8091.
6. Добавить nginx HTTP/server snippets в нужные контексты, сохранив account API,
   HTTPS и текущий CA upstream. Новый более длинный account/support location должен
   обслуживаться support, остальные account URL — прежним CP. В **существующих**
   account proxy locations подключить nginx-account-session.conf, сохранив их
   add_header/TLS/Origin/Cookie/лимиты. Map из nginx-http.conf обязателен. Проверить,
   что login/verify и logout удаляют guest cookie, но не теряют CP Set-Cookie.
   `nginx -t` до согласованного reload. `-account-url` обязателен: обычный HTTPS
   домен сайта либо точный CP endpoint с существующим проверенным CA через
   `-account-ca-file`. Приватные ключи/доступ к CP БД поддержке не передавать.
7. `deploy/support/prepare_overlay.py` формирует три точечные замены из свежего
   сайта и фиксирует before/after SHA256. В staging добавить только виджет и hook в существующий
   site.js и дополнение политики. **Не заменять весь website или account.js**:
   у production есть отдельные lifetime-изменения. Проверить совместимость
   CSP (self scripts/style/connect), мобильный экран, cache busting и health.
8. Проверить настоящую цепочку: два браузера, два разрешённых оператора,
   запрещённый оператор, claim race, reply, reload, «Нет», «Да», забыть сессию,
   временная недоступность Telegram и последующая доставка. Никаких reboot ПК.
9. Безопасный откат исправления: временно отключить widget/API поддержки (503),
   сохранив БД, переписку и account-cookie. Не возвращать доступ через старый
   уязвимый endpoint и не запускать старый бинарник на расширенной схеме. Исправлять
   вперёд либо восстанавливать совместимый проверенный комплект без возрождения
   legacy-доступа. Account/CP/relay работают независимо; дамп не перезаписывает новые обращения.

Токен бота и членство операторов требуется пересматривать при увольнении или
утечке. Перед сменой бота/группы опустошить outbox и явно мигрировать/очистить
Telegram message mappings: ID сообщений относятся к конкретной группе/боту.
Изменение numeric allowlist требует штатного перезапуска только support-службы.

## Проверки

`VELIQ_SUPPORT_TEST_DATABASE_URL` должен указывать на одноразовую тестовую БД:
тесты создают/удаляют только отдельные случайные схемы. `go test -race ./services/support/...`.
Для настоящего браузера дополнительно `VELIQ_SUPPORT_BROWSER=1`, Python Playwright
и Chromium. Telegram имитируется HTTP-сервером теста; реальных сообщений нет.
CI также собирает комплект с manifest SHA256; ни тесты, ни сборка не деплоят сайт.
